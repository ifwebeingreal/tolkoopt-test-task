# Тестовое задание — ТОЛЬКООПТ

## 1. Вопросы к задаче

Перед началом разработки я бы уточнил следующие моменты:

1. Как сейчас рассчитываются цены для клиентов? Есть ли определённая формула, минимальная наценка или какие-то ограничения?
2. Что делать, если одна или несколько площадок не вернули данные? Использовать предыдущие цены или оставлять текущие?
3. Насколько важно обновлять цены строго каждый час? Допускаются ли небольшие задержки?
4. Как сейчас происходит обновление клиентских прайсов? Через Excel, базу данных или API?
5. Что делать, если новая цена сильно отличается от текущей? Кто должен проверять такие изменения?

### Два наиболее важных вопроса

**1. Правила расчёта цен**

Для начала нужно понять, как работает текущая система ценообразования. Например, если есть минимальная допустимая цена, опускаться ниже неё нельзя. Также могут быть ограничения по наценке. От этого будет зависеть логика расчёта.

**2. Что делать при отсутствии данных**

Я бы не стал автоматически менять цены, если источник не ответил или вернул неполные данные. При этом можно использовать предыдущие результаты, если они ещё актуальны. Поэтому нужно уточнить, сколько времени данные конкурентов считаются актуальными.

### Допущения

1. Сбор данных запускается каждый час.
2. Если достоверных данных нет, текущая цена не меняется.
3. Изменения цены более чем на 30% требуют ручной проверки.
4. Старая система продолжает работать до проверки новой.
5. Для расчёта используются только подходящие предложения из успешно полученных данных.

## 2. Архитектура

Я бы постарался использовать существующие решения, а не переписывать всё с нуля. Сначала изучил бы документацию и обсудил с предыдущим разработчиком, как устроены сбор данных и обновление прайсов.

Для реализации можно использовать Python, PostgreSQL для хранения результатов и APScheduler для запуска задач каждый час. На данном этапе не вижу необходимости добавлять микросервисы или брокеры сообщений.

### Как будет работать система

1. Раз в час планировщик запускает сбор цен с площадок конкурентов. Поскольку площадок около 20, запросы можно выполнять асинхронно, чтобы не ждать каждую площадку по очереди.

2. Для каждого источника устанавливается тайм-аут. Если площадка не отвечает, фиксируем ошибку и продолжаем сбор с остальных.

3. После сбора проверяем результаты. Учитываем статус источника, актуальность данных, корректность цен и другие условия, необходимые для расчёта.

4. Полученные данные сохраняем в PostgreSQL вместе с названием площадки, временем получения и статусом. Это поможет разобраться, откуда появилась конкретная цена.

5. Дальше рассчитываем рекомендуемые цены по согласованным правилам. Если подходящих предложений нет, оставляем текущую цену.

6. Если новая цена отличается от текущей более чем на 30%, отправляем её на ручную проверку.

7. Остальные цены передаём в существующую систему обновления клиентских прайсов. Сам механизм обновления я бы по возможности оставил без изменений.

### Обработка ошибок и повторных запусков

1. Если одна площадка недоступна, остальные продолжают работать. Неуспешные результаты не используем для расчёта.

2. Чтобы избежать дублирования, можно использовать уникальный ключ из идентификатора площадки, товара и периода сбора. Если такой результат уже есть, повторно его не добавляем.

3. Также нужно исключить одновременный запуск нескольких циклов обновления, чтобы они не мешали друг другу.

### Переход на новую систему

1. Сначала запускаем новую систему параллельно со старой, но без возможности изменять клиентские цены.

2. Сравниваем результаты двух систем, проверяем расхождения в ценах и возникающие ошибки.

3. Когда убедимся, что всё работает нормально, постепенно включаем новую систему для небольшой группы товаров.

4. Для переключения можно использовать обычный флаг в настройках. При этом важно, чтобы две системы одновременно не обновляли одни и те же товары.

5. Если возникают проблемы, отключаем обновление через новую систему и возвращаемся к старой. Текущие клиентские цены при этом сохраняются.
